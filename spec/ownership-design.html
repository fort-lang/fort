Compiler design / proposal

Static ownership across boundaries

Prove storage validity and ownership effects across calls, fields, and retained references. Reject invalid operations and incomplete proofs.

fort · 2026-09-30 · source basis 414d8b7c
No lifetime annotations · No unsafe construct · No runtime ownership tracking

Proof contract

Status: proposal. This document specifies the intended analysis. D17.13 records the accepted FFI trust rule. The remaining analysis rules remain proposals.

The compiler proves temporal ownership obligations for fort operations in the checked import closure. Reject an operation when a reaching path violates its obligation.

Reject a fort operation when the analysis cannot prove its obligation. Trusted FFI results and effects use the boundary rule below.

  • Do not add source lifetime annotations or lifetime parameters.
  • Do not add an unsafe keyword, block, function qualifier, or compiler proof-bypass option.
  • Do not add allocation headers, generation counters, runtime ownership tables, or new ownership checks in generated code.
  • Keep current mutable aliasing rules. Prove ownership effects even when writable references alias.
  • Keep pointer, span, string, struct, and C ABI representations unchanged.
  • Complete the feature before migrating existing source.

Foreign implementations remain outside this proof. An extern declaration is the implicit foreign trust boundary. Its call requires no additional syntax.

Trust foreign behavior and declared types. A missing foreign body or effect summary alone causes no ownership diagnostic.

Coverage limit. The analysis targets dangling storage, lost ownership, invalid release, and invalid ownership transfer.

It does not establish total memory safety. Existing bounds, nullability, arithmetic, data-race, and foreign-code rules still apply.

Unfreed ownership at a normal scope exit is an error. Abort paths carry no cleanup requirement. Program-wide cleanup of owning globals remains unresolved.

Allocation obligations cover memory, not file descriptors, sockets, or other scalar resources. This design adds no general resource type system.

Storage and ownership

TermMeaning
PlaceA FIR local or global with field, element, or dereference projections. A place contains a value.
Storage sourceA stack object, heap allocation, static object, symbolic caller object, or trusted foreign object.
Allocation identityAn analysis identity for heap storage. It is independent of the place that currently owns the allocation.
Owning placeA reference place marked own, or an owning leaf within an aggregate.
BorrowA non-owning pointer, span, or string with possible storage sources and an offset or subrange where known.
ObligationA requirement to retain, release, or transfer an owned allocation on each normal path.
SummaryAn inferred relation between function inputs, memory effects, obligations, and outputs.

Record place contents separately from source validity. A zero owner place contains no allocation. A released allocation remains invalid after another allocation enters that place.

Keep possible source identities, ownership states, ranges, and witness locations. Separate the lifetime of a span header from its backing allocation.

A heap pointer and an address of its owner slot have different sources. Moving the pointer preserves the heap source but not the old slot address.

A stack object's lifetime ends at its FIR dead marker. A temporary's lifetime ends at its source-defined boundary.

By-value parameter storage ends at each normal return, after deferred effects. Check residual owned parameter leaves even when FIR emits no dead marker.

Reject returned or retained addresses into ended parameter storage. Ending a borrowed parameter's slot does not end the symbolic caller storage it references.

Copies of borrows retain their source relations. Moving an aggregate transfers its owned leaves and borrowed fields. It does not rebase stack addresses.

Track possible overlap between source regions and owner slots. Pointer equality alone does not establish distinct ownership or an allocation extent.

Use finite graphs for recursive types and repeated allocation sites. Widening may lose precision; it must not remove ownership obligations.

Strong updates require one proved destination. Weak updates preserve the alternatives of destinations that can overlap. Unknown fort effects preserve uncertainty.

Do not identify successive allocations solely by their source expression. A loop can create multiple live allocations at the same expression.

FIR transfer rules

Run the analysis on verified FIR before build-mode transformations. Read types, places, calls, moves, and deferred expansions from FIR.

OperationRequired facts and state change
allocCreate a fresh allocation obligation. Record the element type and extent when available. Existing allocation failure paths abort.
Borrow copyCopy source relations without transferring ownership. Record retained relations for aggregate fields and elements.
moveTransfer ownership and borrowed contents. Set the source place to zero. Preserve views into live heap storage.
delRequire valid allocation ownership. Discharge that obligation, invalidate its allocation, and empty the operand place.
Empty delAccept. No allocation exists to release. Keep the empty state.
Owning assignmentEvaluate the right side first. Require the destination's previous ownership obligations to be empty or already transferred.
Aggregate assignmentApply ownership rules to the owned leaves. Do not discard fields hidden inside nested aggregates.
addrProduce a borrow of the addressed storage. Taking an address does not end tracking of that storage.
slice, .ptrPreserve the backing source and known offset or range. These operations do not transfer ownership.
slice_ptrRequire a proved source and sufficient extent for fort storage. Trust foreign storage validity and extent. Add no runtime range check.
castPreserve known sources and byte ranges. Type erasure does not erase an obligation. Integer reconstruction alone establishes no source.
Memory accessRequire live fort source storage and a valid extent. Trust foreign storage validity and extent. Keep existing type rules.
callInstantiate the summary with actual arguments and aliases. Apply effects in their proved order.
deadEnd stack storage. Report ownership obligations that remain in the dying place. Reject borrows that escape the storage boundary.

Keep del shallow. Release or transfer owned descendants before deleting their containing allocation.

A zero-element allocation still creates an ownership obligation. A zero-length owning span differs from an empty owner.

Keep allocation ownership separate from access extent. A zero length alone does not prove that an owner has no allocation.

A transferred descendant keeps its identity. Deleting the old container does not release that transferred allocation.

Do not use a removed overwrite check as proof that a destination is empty. The static result must hold in release builds.

Ordinary span bounds keep their current runtime checks. Raw-pointer spans into fort storage require static extent proof. Foreign storage uses FFI trust.

Reading the zero value of an emptied owner remains legal. Comparisons with null and zero span lengths remain legal.

Reject dereferencing an owner that the analysis proves empty. Reject semantic use of a borrow whose source is released.

A store that replaces a dead borrow need not read its old value. Permit reinitialization from a valid source.

Do not free storage through a borrowed reference. Existing type checks continue to reject adding own or mut through a cast.

Control flow and cleanup

Propagate abstract states along reachable FIR edges. Join possible source relations and ownership obligations. Retain witness locations for each failing alternative.

Different branch states are legal when subsequent operations satisfy both states. Do not reject a join merely because one path has an empty owner.

Refine direct null tests. Preserve the correlation between the selected branch and the tested place until an overlapping write changes that place.

A known-null path carries no allocation obligation. Do not report a leak merely because an owning call can return null.

Compute loop states to a fixed point. Keep the zero-iteration path. Do not promote untouched empty places to live places.

Require each iteration to preserve or discharge the obligations that reach its next iteration. Check scopes crossed by break, continue, and return.

Conditional expressions and short-circuit operands already have FIR edges. Analyze their moves through those edges instead of banning their syntax.

Read deferred releases where FIR expands them. Apply reverse registration order. Check returned borrows after all deferred effects on that exit.

Use borrow liveness to permit a release after the last semantic use. An unused dangling local alone does not require an error.

An escaping fort result or retained fort field has a caller obligation. Local last-use analysis alone cannot discharge that obligation.

Runtime failures, panic, and other abort paths do not run ordinary cleanup. Do not require them to discharge ownership obligations.

Apply inferred call exit outcomes to reachable continuations. Remove a normal continuation only when the instantiated summary proves that no normal return occurs.

Unknown or incomplete summaries keep a possible normal continuation. A function without a noreturn type can still have no normal return.

Do not derive safety from a runtime check that a build mode removes. Static verdicts remain independent of release and bounds-check options.

When a loop or recursive summary loses precision, report failure to prove the affected operation. Do not suppress further analysis by declaring it escaped.

Function summaries

Infer summaries from all available fort bodies in the import closure. No programmer-written lifetime relation is required.

Use symbolic caller storage for borrowed parameters. Distinguish a by-value parameter's stack storage from heap storage that its fields reference.

Summary partRequired content
PreconditionsLive sources, required extents, empty output owners, and alias relations that the body requires.
Owned inputsOwnership consumed, released, returned, or stored through a parameter or global.
Borrowed outputsSource relations for returned pointers, spans, strings, fields, and output parameters.
Retained inputsSource relations that persist in fort fields, elements, or globals after an analyzed fort call.
Memory effectsReads, writes, releases, and transfers with the order needed for alias-sensitive obligations.
Conditional effectsRelations between relevant return values, branch predicates, and output ownership or sources.
Exit outcomesNormal-return reachability, abort outcomes, and unknown outcomes, with relevant input conditions.
Result storageThe caller destination for aggregate _0, including possible aliases with arguments and globals.
CallbacksPossible targets, invocation effects, borrowed argument sources, and known retention behavior.

Instantiate symbols with caller places and source identities before applying effects. An own argument transfers ownership; a borrowed argument does not.

Do not treat two formal parameters as distinct allocations. The caller can supply the same place through both parameters.

Bind aggregate _0 to the actual destination. Include its aliases with arguments and globals before applying result writes.

In s = f(&s), result storage can alias an input. Do not model that result as private fresh storage.

Check previous owner obligations at overlapping writes. Preserve FIR ordering of result writes, reads, and deferred effects.

A pointer to an own slot permits summarized ownership changes in that slot. Taking the pointer must not disable overwrite or leak checks.

Infer a returned borrow's sources independently for each possible result path. A borrowed input can become a returned borrow without becoming owned.

Infer retained-source relations through intermediate fort calls. Preserve trusted foreign result classification through wrappers. Hidden foreign effects remain outside the proof.

Compute summaries across recursive call groups to a fixed point. An incomplete recursive summary is unknown, not an empty effect set.

For indirect calls, combine summaries of possible fort targets. Extern targets use FFI trust. An unknown fort target cannot establish a safe memory effect.

Check a library body with symbolic inputs under --check. Inferred caller requirements belong to its summary.

A local stack escape is invalid independently of caller inputs. Reject it in the callee. Report an unsatisfied caller requirement at the call.

Summary graphs need relational state. Unordered may-read and may-free sets alone cannot prove Example 10.

Keep summaries in the current analysis. Module-cache serialization remains outside this proposal.

Fields and retained references

A reference field holds a borrow source relation or an ownership obligation. Its containing object's lifetime does not extend its target's lifetime.

Track relations through nested structs, fixed arrays, heap objects, and globals. Do not stop tracking when a value enters an element.

Track borrowed fields when aggregates copy. Transfer owned fields when aggregates move. Record caller relations for returned aggregates.

For unknown indices, retain possible overlap with the collection's element set. Prove distinct elements before applying independent destructive updates.

Replacing vector backing storage invalidates views into the earlier allocation. A pointer to the vector object can remain valid.

A retained string key depends on its character allocation. Copying the string header into a map does not make the characters owned.

A pool view can refer to an allocation reachable through the pool's owned chain. Adding another block need not invalidate earlier block views.

Releasing the pool invalidates views into the blocks it releases. Proving an unbounded chain release requires the recursive heap rules below.

An aggregate can contain an owner and a view into its heap allocation. Moving both preserves that view while the allocation remains live.

An aggregate can instead contain a view into its own stack fields. A move does not repair that stack address.

Retained relations can end when a field is cleared or replaced. Dynamic containers need proof that no retained element still exposes the source.

Extern boundary

Accept FFI as trusted under D17.13. An extern declaration requires no unsafe construct, lifetime annotation, compiler contract, or effect summary.

Trust the declared ABI, types, and ownership convention. Check known fort argument sources before the call.

An own input leaves its fort source place. An own result creates a fresh obligation under the foreign declaration's uniqueness promise.

A borrowed result has a trusted foreign source. Permit access and slicing without a proved source relation or statically established allocation extent.

This trust does not prove non-nullness, initialization, alignment, or the foreign allocation's lifetime. Foreign callers and implementations must satisfy those requirements.

Keep known fort ownership facts across the call. Missing foreign summaries do not invalidate those facts or block later cleanup.

Apply ownership transfers expressed by the signature. A borrowed argument alone does not transfer ownership.

Hidden foreign aliases, retention, releases, writes, and callbacks remain outside the proof. Do not infer that foreign code actually has no effects.

A foreign result can alias fort storage. Without a source relation, later fort deletion cannot invalidate that result in the analysis.

Preserve trusted foreign source classification through copies, casts, fields, returns, and fort wrappers. Keep other fort source relations checked.

A raw cast alone cannot create foreign trust. Arbitrary integer-to-pointer casts remain subject to the fort proof rules.

Proof limit

FFI can violate the ownership proof. In particular, foreign code can return dangling pointers or release storage that fort still owns.

Ordinary extern calls and their returned references need no compiler metadata. This version adds no compiler contract system.

Optional foreign-function summaries can add checking in a future design. Their format, precedence, and handling of indirect calls remain unspecified.

Diagnostic contract

Use the existing source diagnostic format from spec/toolchain.md section 4. Compilation errors exit 1.

<file>:<line>:<column>: error: <message>
<file>:<line>:<column>: note: <message>

Columns count source bytes from 1. Attach notes to their error. Underline the source token or range that the diagnostic identifies.

ClassReport
Proved invalid useName the borrowed place and the release, move, or storage end that makes the access invalid.
Path-dependent invalid useName the place and a reaching path that invalidates it. Keep that path's witness location.
Unproved useState that the compiler cannot prove live storage, extent, alias requirements, or completed cleanup.
Lost ownershipName the owning place at overwrite, release, or scope end. Note the source of its obligation.
Unsatisfied call requirementReport at the call. Note the relevant callee operation and substituted caller alias or source.
Analysis limitReport the unresolved operation and the precision limit. Do not claim that the program definitely has a memory error.

The examples specify primary errors and relevant notes. Suppress dependent cascades for that operation while retaining other independent obligations.

Proposed wording is not current compiler output. The current compiler does not implement this analysis.

Check and build modes use the same ownership analysis. JSON keeps the existing diagnostic schema and includes the same error and note ranges.

A stricter future rule can reject reads after move or del. It requires a separate place state without changing allocation identity or summary relations.

That stricter rule breaks current zero inspections. Repeated empty del can remain legal under either rule.

01Local view after deletion

A view retains its allocation source after the owner becomes empty.

ex01_local_view.ftReject
fn demo() i32 {
    i32 mut* own p = new(i32);
    i32* q = p;
    del(p);
    return *q;
}

                ^
ex01_local_view.ft:4:5: note: 'p' released the allocation here
        del(p);
        ^~~
ex01_local_view.ft:3:14: note: 'q' borrows the allocation here
        i32* q = p;
                 ^

Read q before del(p). A null test on p does not restore q.

02View across an ownership transfer

A heap view follows the allocation. It does not depend on the current owner place.

ex02_transfer.ftAccept
fn demo() i32 {
    i32 mut* own p = new(i32);
    *p = 7;
    i32* view = p;
    i32 mut* own next = move(p);
    i32 value = *view;
    bool empty = p == null;
    del(next);
    return empty ? value : 0;
}

Expected diagnostics · proposed output

None.

The transfer empties p. The allocation remains live in next until del(next).

16Loop-carried ownership

19Trusted extern calls and results

Unresolved cases and proof limits

These 12 entries contain nine unresolved fort cases and three FFI proof limits. Hidden foreign behavior remains outside the proof.

Reject fort operations where missing information prevents proof. Apply FFI trust to foreign proof limits. The excerpts are not complete test files.

U1. Recursive heap cleanup

node mut* own next = move(current->next);
del(current);
current = move(next);

Missing: a finite heap model that proves an unbounded owned chain empties without merging distinct live obligations.

Consequence: the intended list and pool idioms need inductive cleanup proof. An allocation-site set alone cannot establish it.

U2. Dynamic element identity

node* view = slots[i];
del(slots[j]);
use(view);

Missing: index equality, inequality, range partitions, and ownership state for unbounded elements.

Consequence: reject the use when i and j may select the same allocation. Do not assume distinct indices imply distinct targets.

U3. Bytewise writes to reference fields

copy_bytes(cast(&dst, u8 mut*), cast(&src, u8*), sizeof(box));

Missing: a representation-aware rule for copies, overlaps, partial writes, and padding around borrowed or owning fields.

Consequence: fort bytewise writes need representation-aware proof. Foreign bytewise writes use FFI trust; hidden ownership duplication remains outside the proof.

U4. Unknown extern retention and global access

foreign_keep(view);
del(owner);

Outside proof: hidden foreign retention and global access.

Consequence: accept foreign_keep and subsequent del(owner) when known fort obligations permit it. Foreign use of the retained view can then dangle.

U5. Foreign buffer invalidation

char* first = foreign_text();
foreign_text();
use(first);

Outside proof: reused buffers, handle closure, and library-managed storage validity.

Consequence: accept use(first) under FFI trust. The foreign implementation must keep the result valid; the compiler does not prove it.

U6. Callback sources and indirect targets

foreign_sort(base, count, width, compare);

Outside proof: foreign callback timing, argument validity, and retention.

Consequence: trust arguments supplied at foreign entry points. Analyze each fort callback body with symbolic caller storage and ordinary fort ownership rules.

U7. Returned self-references

value.view = &value.inline_field;
return value;

Missing: precise treatment of aggregate result storage and borrowed addresses into copied or moved stack values.

Consequence: reject the escaping inline-field address. A view into separately owned heap storage can follow the transferred allocation.

U8. Analysis precision and termination

return choose ? left(field(next)) : right(field(previous));

Missing: access-path widening, relational predicates, recursive summary termination, and resource limits.

Consequence: publish measured limits and report incomplete proof. Never terminate analysis by accepting the affected operation.

U9. Owning globals at program exit

GLOBAL = move(local);
return 0;

Missing: the final obligation boundary for reachable owning globals and library entry points.

Consequence: distinguish lost local ownership from transferred global ownership. Do not claim program-wide leak detection before this rule exists.

U10. Pointer identity reconstructed from integers

u64 bits = cast(pointer, u64);
u8* restored = cast(bits, u8*);

Missing: whether exact unmodified round trips may retain provenance and which arithmetic destroys that relation.

Consequence: the first version rejects access through restored unless it retains a proved source. Arbitrary integer bits never establish ownership.

U11. Borrows into zero-length or interior allocations

u8* tail = bytes[bytes.len..bytes.len].ptr;

Missing: access rules for empty spans, end pointers, and alignment changes within fort storage.

Consequence: distinguish a live allocation from an accessible byte. A non-null pointer does not prove a nonempty range.

U12. Source evaluation order

items[change_owner(&items)]

Missing: the rulings tracked by T-262 and T-263 for span-header reads and range-loop length reads.

Consequence: analyze the FIR order that the compiler emits. Do not establish source-level guarantees from an unratified evaluation order.
